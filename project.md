**2. Problem, User, Outcome**
- Problem: family finance is scattered across receipts, bills and memory — spending goes untracked, savings targets drift, bills get missed.
- User: self, self-hosting across Android phone and laptop/Pi. Architecture built to be forkable for other self-hosters later.
- Outcome: easily check and track your spending, take the hassle out of saving, never miss a bill.

**3. Minimum v1 Scope**
- Dashboard: spend, savings, due — visible without scrolling, order Spend, Due, Savings
- Spend/Savings/Due pages: itemised, date-ordered, edit/confirm/reorder/filter
- Phone: capture-only (photo or manual entry), auto-downloads to Downloads folder, one-tap refresh to view synced data
- Desktop: full editor — OCR (Tesseract.js), categorisation, Brave tips, auto-ingest from synced folder via File System Access API
- PWA daily notification (Android-only)

**4. Explicitly Out of Scope (v1)**
- Email forwarding of invoices/bills — no static-site path without a real backend, revisit as a deliberate protocol.md 3.3 deviation later
- Multi-layout dashboard, government announcements, granular receipt-level search — all nice-to-haves, not started
- Per-person accounts/logins. Multi-user arrived in v2.1.0, but as *attribution* — a name and a colour on an entry, with anyone able to switch who they're being — so the no-backend, no-login stance in §5 still holds. Real accounts would reverse it.

**4b. Android Release Procedure**
- Sideloading a new APK over the old one keeps the data. Android replaces the APK and leaves `/data/data/com.jaquesbody.sorted/` — where the WebView's IndexedDB lives — untouched. Two things have to hold, and both are now pinned in the repo: `applicationId` is the literal `com.jaquesbody.sorted` in `capacitor.config.json` and `build.gradle`, and the APK is signed with `android/debug.keystore`.
- **No auto-update, deliberately.** An updater swaps the code that reads the data before the user has seen it work, so a migration bug becomes data loss instead of "I hadn't installed that one yet". Rollback also gets worse, and it would need a delivery mechanism — Play Store, or a self-hosted updater with its own APK and a real signing key — which breaks the no-backend property in §5. The manual install is the safety property, not an inconvenience.
- The real data risk is not the update mechanism. In order: a migration bug in a new build (ours, not Android's — so run it against a *copy* of real data first); forgetting to export; and a keystore that quietly changes.
- The signing key is committed, and it is a *debug* key signing nothing anyone cares about. That is the point: it makes the repo buildable into an installable update from any machine.
- The key silently rotated once, between 2.3.0 and 2.4.0 — 2.0.4–2.3.0 are signed `44:00:1E:44…` and 2.4.0 onward `F8:35:75:56…`. Anything on 2.3.0 or earlier could not have updated to 2.4.0 without an uninstall, which is the one thing that does wipe the data. Caught by comparing `apksigner` digests against `keytool`; two different `debug.keystore` files existed (`~/.android` and `~/.config/.android`) and the build was using the one the repo knew nothing about. Now pinned, and the fingerprint is written into `build.gradle` so a change is obvious.
- After any build, check the signature still matches: `apksigner verify --print-certs sorted-v2-<ver>-debug.apk` against `keytool -list -v -keystore android/debug.keystore -storepass android`. Two different digests means the next install will be rejected.
- Release builds are deliberately left unsigned. A release would need a real key, which is a genuine security boundary; the app is sideloaded and doesn't need one.

**5. Architecture Decisions**
- No backend, no cloud storage, no login
- OCR: Tesseract.js, client-side
- Brave API: user's own key, local storage, popup with ignore option
- Sync: Syncthing-watched Downloads folder, one-way auto-download from phone (anchor download attribute — subfolder nesting unverified, test on-device first), desktop watches via File System Access API (desktop-only), phone viewer is manual one-tap refresh
- Notifications: Web Notifications API in an installed PWA, Android-only, flagged on the GitHub page
- Data model: recurring flag + frequency on Spend/Due items. One item per uploaded document (sub-lines for itemised charges within a single bill, not separate items). Direct Debit collections on a bill are payments, not separate charges. Recurring + DD items default to paid=true on upload, confirm button overrides.
- Receipts are stored on the item itself as a downscaled data URL (max 1400px, JPEG), not as a file reference — there is no file system to point at in a browser or a WebView. PDFs are flattened to a first-page image, which is what OCR reads and what's shown, so one copy serves both. Receipt images ride in the JSON export, so a backup stays self-contained; they are not part of the merge-dedupe key.
- A paid bill leaves exactly one record: the copy `markDuePaid` writes into Spend, keeping the original `dueDate`. The Bills Due month view reads those back as its history, which is why paying a bill leaves a "Paid" row in the month it was due rather than in the month you paid it. Each occurrence therefore appears once per month — either paid in Spend or still owing in the due store — with no double count and no gap.
- Overdue bills ride along in the month view, but only when looking at now or the future. A past month is a record of what it held; dragging today's overdue pile into it made the history unreadable.
- Theme and passcode live in localStorage, not IndexedDB: they're device settings, not finance data, and the passcode has to be readable synchronously at launch to decide whether to show the lock screen.
- Passcode is stored as a salted SHA-256 (crypto.subtle, with a non-crypto fallback for insecure contexts). It is a shoulder-surfing screen only — the hash sits next to the data on the same device, so it is documented as such rather than sold as encryption.
- Idle locking uses a `lastActivity` timestamp rather than counting events, so a backgrounded WebView that has its timers throttled can't drift the clock; a backgrounded app is re-checked on `visibilitychange`.
- Every id read, written or deleted goes through `normaliseId()`. It started as a read-path fix and had to be added to `updateItem()` as well: an edit carries the id as a string off a data attribute, and putting a legacy numeric-keyed row back under the string "3" silently creates a *second* row instead of editing the first. The original keeps rendering, so the edit looks like it did nothing. The lesson worth keeping: normalising a key at only some of the call sites is worse than not doing it at all, because each individual site looks correct.
- A JSON value interpolated into a double-quoted HTML attribute has to be HTML-escaped as well as JSON-encoded. `JSON.stringify` emits double quotes; those close the attribute early and leave a truncated, syntactically invalid handler on the button. The failure is invisible — the button renders, it just does nothing when pressed.
- The test suite calling `saveItem()` directly instead of pressing Save is what let both of those through. Behaviour that lives in a click handler has to be tested by clicking.
- List rows are top-aligned, and the sub-line (what a bill is, or when it was paid) takes the row's full width and sits hard right underneath. Centring the row looked fine until a title wrapped, at which point the amount floated in the middle of a two-line block.
- Each Reports card carries its own total under a rule rather than a separate Summary card repeating all three. Reading one number used to mean scrolling past two other cards, and a total belongs with the breakdown it adds up to.
- An off-list category stays offered on an existing entry. Otherwise editing something categorised "Food" would show the select falling back to its first option and rewrite the category on save — the dropdown would change real data because the list changed.
- Bill reminders are bills only, and only while the app is in the background. The platform sets the ceiling: a static site with no backend cannot run a job at a set time and push needs a server, so the check happens when the app is closed, opened, and hourly while open. That limit is stated in the UI rather than left to be discovered, because "it didn't remind me" otherwise reads as a broken feature. A bill is announced at most once a day, and changing the lead time forgets what has already been said, since a different set of bills is then in range.
- A shared icon only works where its class sets `fill: none` and `stroke: currentColor`. The goal tick reused the confirm tick, whose polyline relies on `.confirm-btn svg` for both, so under a different class it filled solid and rendered as a small black arrow. Marks that carry meaning state their own stroke.
- Icons in a row's action column stack in a fixed-width column rather than sitting side by side. Side by side, the column's left edge moved depending on how many marks a row had, so nothing lined up down the page; a fixed width fixes it without the row shifting when state changes.
- Cash is an account of type 'cash', not a payment method. "Paid cash" is then an allocation like any other, and there is one concept to learn instead of two.
- An account's balance is derived, never stored: opening + adjustment + transfers in − transfers out − spend − bills − goals. Storing it would mean the next entry silently overwrote a manual correction, which is the one thing an editable number must not do. A paid bill's payment is already a spend record, so it is never counted twice — the bills split exists for display only.
- "Whose" and "From account" are separate fields. Whose money it was and where it came from are different questions, and a shared joint account cannot be expressed if one field answers both.
- The opening balance is what an account holds *today*, not what it held when tracking started. Transactions that predate the account aren't allocated to it, so an opening figure from months ago would double-count everything since.
- Cash is created on boot rather than by the seed, because an install seeded before accounts existed still needs one — the seed only ever runs on a fresh database.
- Removing an account keeps its entries. They show "Unassigned" until someone re-picks one, because silently reassigning money is worse than showing it as unattributed.
- **An unterminated CSS comment silently kills the rules after it.** One missing `*/` left `.goal-tick`, `.report-total` and a third rule unparsed while braces still balanced and the page still rendered — so a report total quietly stopped being right-aligned and nothing said why. There is now a test that counts comment markers, and one that asks the browser whether a rule in the file is in the parsed stylesheet.
- **Two lines drawn on identical pixels read as a third colour.** With no bills in a window, Total est costs and Spend are the same number; drawn over each other they looked like a purple line that was in no legend. The bold one is now skipped when it would coincide with a thin one.
- Bills paid before 2.8.3 exist only as a payment copy in Spend. Reading them as Spend put a month of rent under the spending line and left Bills at zero; they are read as Bills now.
- **The Dashboard trend counts bills.** It drew from the Spend store only, which was free while paying a bill wrote a payment into Spend. Since 2.8.3 it does not, so a month whose only activity was paying bills drew as an empty month — the month a trend is most worth looking at.
- **Spend draws no projections.** A recurring Spend entry projected its next occurrence as an inert row with nothing to tap. Spend is for the one-offs; anything that repeats belongs on Bills.
- **A paid bill can be un-paid and can be edited.** The tick was a non-button, so there was no way back, and the row opened the *spend* editor for a payment record that no longer exists — which is why it looked uneditable.
- **Deleting a repeating bill asks which one it means.** The series is carried by its upcoming row, so deleting that row ended every future occurrence without saying so. "This month only" and "the whole thing" are now named choices.
- **A rule that parses is not a rule that works.** A stray `.btn` with no brace turned the next rule into the descendant selector `.btn .choice-row`: valid CSS, one rule, correct brace and comment counts, matching nothing. Committing it cost a release of a dead dialog. The guard is now a list of selectors the markup depends on, asked of the browser's parsed sheet — see `.setting-row--inline` for the same family of failure.
- **The paperclip means there is a picture.** It sat on every row, dimmed, as the way in to attach one, so eight expenses had the same icon eight times and nothing said which had a receipt. It appears only when there is one; attaching is in the row's editor.
- **A render is for the page it was asked for, and it fails loudly.** `renderPage()` read `currentPage` *after* awaiting the people and account loads, and each render function captured `renderToken` itself — so a render superseded while loading picked up the newest token and was allowed to paint. That is how a slow page could leave the wrong tab on screen with the nav highlighting the right one. Both are now captured at entry, and a superseded render bails before dispatching.
- **Nothing re-rendered on resume.** Android suspends the WebView in the background and closes IndexedDB while it is away. Anything that rendered in that window failed, and nothing re-read on the way back — so you returned to a blank or stale page under a nav highlighting the tab you had just asked for. The heaviest page is the one that suffers most, which is why it looked like a Reports problem. Returning to the app now re-renders the current tab.
- **A failed read retries, then admits it.** Swallowing the error left the old page sitting there; the retry re-opens the connection first, and if it still cannot read, the page says so with a Try again button rather than going blank.
- **The sync button floats; it does not join the toolbar's flow.** Adding it as a flex child meant right-aligning the dashboard's toolbar, which slid the month selector across the screen and put it somewhere the other three tabs do not have theirs. The month navigator is at a fixed width *and in one place* on Dashboard, Spend and Bills, and a control in two positions reads as two different controls harder than one in two widths. It is now absolutely positioned, out of the flow, so the selector does not move.
- **A test reminder has to survive the thing that cancels it.** Nothing arrived on first release, for two reasons and both were real. `scheduleAllReminders` cancels everything and rebuilds from the plan, and the test was not in the plan — so putting the phone down and picking it up again, which is the entire procedure, threw it away. And `allowWhileIdle` was false, so an alarm that will not fire while the screen is off defeats the point of a button whose whole purpose is that you put the phone in your pocket and wait. It now records its fire time and is re-issued after every rebuild, and an empty plan no longer short-circuits past it.
- **A settings row is one line, and the rule that said so had never worked.** `.setting-row--inline { flex-wrap: nowrap }` existed and was declared *before* `.setting-row { flex-wrap: wrap }` at the same specificity, so the later rule won and every "inline" row was free to fold. On a 360px phone all three Reminders rows came out as a label with the picker and the switch underneath it. The fix is not the dead rule but a `.setting-row--nowrap` modifier declared after the base rule, applied only where folding is wrong — a text field wants the width, a label-plus-switch does not.
- **In a nowrap row the label keeps its width and the control gives ground.** Priority is the whole mechanism: if the label were the shrinkable one, "Record spending" would wrap onto two lines and buy nothing at all. Two labels lost a word to make this possible ("Spending", "Goals") because a 124px label, a 118px picker-and-switch minimum and a 15px gap do not fit a 230px card. `flex: 0 0 auto` on `.setting-row--inline .setting-text` is load-bearing and has a test.
- **A heading can fail by one pixel, and one pixel is not a fix.** "Where Your Money Is" plus a four-figure total came to 145px of text in 144px of space at 360px, and the same edge returned at 393px with a five-figure total. The room came from the gap, the heading and the total together, under a 430px query rather than 380px, because the failure was reported at a width no existing breakpoint covered.
- **Line boxes, not `getClientRects()`.** A block element's `getClientRects().length` is always 1 and cannot see a wrap at all — which is how a three-line Reminders card was measured as fine, repeatedly. Counting merged rect tops over a Range over the text node is the only measure that matches what a person sees. It is now in the suite, at a real 360px viewport, because 412px hid this.
- **Sync is one address and one button.** The card was four rows plus a paragraph about running the host. What was asked for was the simplest thing that works: pick where, paste the address, press Sync now. The status row went with it — the button is enabled when it will work and disabled when it will not, which already says "Ready" and "No address set" without a line to read.
- **Total money is the top of the Dashboard because it is the question the other cards are about.** Spent, due and saved are three answers to "what have I got", and until the whole figure is visible each reads as the whole figure. The bar is four parts because the grey one is the interesting one: three coloured bars show commitments, the remainder is what survives them. Savings is measured against the target the user set rather than treated as an invoice, because a goal is an intention. The per-account breakdown left Reports in the same pass — it was a second line under every account, and it is this bar's job now.
- **The forecast's month in progress counts, in proportion.** It used not to, which was defensible arithmetic and read as a dead figure: record £300 today and nothing on the forecast moved. Counting it as a *whole* month was worse and had been tried (£100 six times plus £10 logged two days in averaged £85). So the month in progress contributes what was spent against the share of it that has happened. The cost is honest and worth stating — five days into a month with nothing logged reads as a slower pace than usual, so the figure sits a little under the completed-month average and converges as the month fills.
- **A status bar icon must be a silhouette.** It was the launcher icon, which Android tints into a featureless white blob: a rounded square with a background layer means nothing in a monochrome slot. `ic_stat_sorted` is one stroked path and nothing else — no fill, no background — inside the 24dp box with the padding Android requires.
- **Tailscale is not a different transport, it is a different address.** The sync unit is one HTTP file, so pointing it at a Tailscale IP is the whole of the integration: the host runs exactly as it does for LAN, the address is stable wherever the machine is, and it works from a phone that is not at home with nothing exposed to the internet.
- **Not holding `SCHEDULE_EXACT_ALARM` is only half the decision; the plugin defaults to demanding it.** `LocalNotificationsPlugin.schedule()` opens Android's "Alarms and reminders" settings screen — taking the user out of the app — whenever any notification in the batch has `isExactNotification` set, on Android 12+, when the permission is absent. And that flag **defaults to true**. So removing the permission while leaving the default alone means the first `schedule()` of every launch throws the user into Settings and the app is unreachable until they come back. It made 2.30.0 unopenable, and only surfaced there because that was the first release in which `schedule()` reached native code at all. Every notification now carries `isExactNotification: false` through one `INEXACT` constant, because the two halves of the decision have to agree: dropping the permission and then asking for exact alarms anyway is just a permission prompt with extra steps.
- **A flag whose absence is silent needs two guards, not one.** A runtime check that every object handed to the plugin opts out, and a static check that every notification literal in the source carries it. The second is what catches a call site added later and forgotten, which no run can reach. Both were verified by planting the omission.
- **A vanilla Capacitor app has to load the runtime itself, and nothing tells you.** The Android build injects `native-bridge.js`, which is a *different file* and does not define `registerPlugin`; the CLI does not copy `capacitor.js` into `webDir`. So this app shipped with a `window.Capacitor` that answered `isNativePlatform()` perfectly and then threw on every plugin call: reminders never worked, and `exportData()`'s Filesystem/Share pair failed the same way. `capacitor.js` is now committed to `docs/` and loaded ahead of everything. Two tests hold it: one asserts the runtime is present and a plugin can be reached, one asserts the committed copy has not drifted from the installed `@capacitor/core`.
- **A stubbed global is not the same as the real one.** This is why the above survived sixteen releases and every notification test passing. The probes overwrote `window.Capacitor` with an object that *included* `registerPlugin`, so every test exercised a global the app never had on a device. The lesson generalises past this bug: a fixture that supplies the thing under test proves nothing about whether the app has it. The runtime test now reads the real page load.
- **A missing runtime should fail in words.** `notifyCap()` throws a sentence naming the problem instead of a TypeError naming an internal function, because "this build is broken and here is a function name you cannot act on" is the least useful thing an app can say about itself.
- **Sorted's alarms are inexact, and that is why a reminder cannot be watched for.** The app deliberately does not hold `SCHEDULE_EXACT_ALARM` (it needs its own grant on Android 12+ and Play restricts it to clock apps), so `canScheduleExactAlarms()` is false there and the plugin falls back to `setAndAllowWhileIdle`. Android gives no timing guarantee for an inexact alarm. That is correct for "Rent is due Thursday" and useless for anything being watched, which is why there are two test controls and not one: **Show one now** is dated in the past, which makes the plugin post it in-process and proves permission, channel and rendering immediately; **Arm one** is a real alarm five minutes out, which proves AlarmManager accepted it. The first version promised one minute and was simply wrong about what the system had agreed to.
- **The nudge pickers stay at whole hours.** "None of the reminders are minute specific" is true, and deliberately so: both nudges are daily, and 8:05pm is not a meaningfully different reminder from 8pm. A finer control would be a second thing to be wrong for no gain. The test button is the instrument for checking delivery, and it is now reliable.
- **A flaky test in the place that guards a real bug is worse than none.** The rapid-switch test read the DOM after a fixed 110ms, which is shorter than Reports takes to build a forecast and draw a chart — so it intermittently reported the previous page and looked exactly like the 2.23.0 fault coming back. It waits for the page now, bounded, and three consecutive runs are clean.
- **A test reminder goes through `schedule()`, never around it.** A button that posts a notification directly would prove the one part that is least likely to be broken. Scheduling it a minute out exercises the permission, the channel, the alarm and the delivery together, which is the only way to tell whether the phone is actually delivering anything without editing real data to make a bill due. It carries its own id so no real reminder is cancelled or confused by it, and nothing marks it as seen.
- **Bill reminders cannot be made to fire quickly, by design.** The intended moment is a fixed hour (`NOTIFY_BILL_HOUR`), so the earliest a bill reminder can ever be is tomorrow morning. That is why the test control exists rather than a "remind me in 10 minutes" option that would be a second scheduling path to keep correct.
- **The pending list is read from the phone, not from what Sorted believes it asked for.** `pendingReminders()` existed for exactly this and was never called. The two can disagree — a withdrawn permission, an alarm dropped by the system's battery rules — and a switch showing "on" is not evidence that anything will arrive.
- **Settings must not wait on a bridge call to appear.** The pending list is a bridge call, and awaiting it before rendering meant that a slow one — or a half-installed plugin that never answers — left Settings not appearing at all, showing whatever was on screen before. This is the stale-screen fault from 2.23.0 recurring in a new place, and the rule generalises: a render draws what it already has, then fills in what it had to ask for.
- **A wrong function name inside a try/catch fails quietly.** "Send a test" shipped calling `notificationPermissionGranted` instead of `notifyPermissionGranted`; the ReferenceError was caught and shown as a toast, so nothing but clicking it on a phone would have revealed it. There is now a test that every name used in an inline handler exists, because that is not a class of mistake a linter catches here and not one the suite reached on its own.
- **A hint long enough to fill its column pushes the control onto its own line.** The test row's hint did, which broke the "each row on one line" rule the rest of the Reminders card keeps. The copy was shortened rather than the rule relaxed.
- **Sync moves a snapshot, not records — because a delete is not a record.** `deleteItem()` erases the row outright: no tombstone, no `deletedAt`. A record-level merge ("last write wins on `updatedAt`") therefore cannot tell a bill deleted on the phone from one that never existed on the laptop, and resurrects it every time the devices meet. Tombstones plus a garbage-collection policy is the alternative, and it is a much larger thing to get right for no gain at this scale. With snapshots a delete is an absence, and absence travels. The cost is stated rather than hidden: if both devices change things before either syncs, one side is overwritten — and the local copy is backed up before that happens, with a Restore control for it.
- **A snapshot is stamped with when the data changed, not with now.** This was a real bug, caught by the first end-to-end test. Stamping with the current time made a freshly built snapshot newer than the server on every pass, so the app pushed every time, could never recognise that it had nothing to send, and could never pull. Records' own `updatedAt` is not sufficient on its own, because deleting the newest row leaves every surviving row untouched and the change would look like it had not happened — so every write, delete and wipe records a stamp of its own via `dataChanged()` in db.js. Applying a snapshot suppresses that stamp, or each sync would end by marking the local copy newer than the file it came from and immediately want to push it back.
- **A pull replaces; it does not merge.** `importDataToDB` in merge mode mints new ids and keeps local rows the file doesn't have, which is precisely the resurrection snapshots exist to prevent. Sync therefore uses `replace`. A pull rewrites every row and mints fresh ids, with person and account references remapped by name so the result is coherent.
- **Sync goes through the native HTTP stack, not the WebView.** The app's origin is `https://localhost`, and Android blocks cleartext by default at API 28+ (this app targets 36). `CapacitorHttp` sidesteps mixed content and CORS in one move, because the request never passes through the WebView. That leaves exactly one gate — the OS cleartext policy — answered by `network_security_config.xml`.
- **That config is the one place this app is weaker, so it says so in full.** Android addresses hosts by name or literal address and cannot express "only RFC1918 ranges", so permitting a home server on a dynamic IP means permitting cleartext generally. HTTPS traffic is untouched, no data goes anywhere by permitting a protocol rather than opening an endpoint, and the file documents exactly what is being traded and how to revert it. Recorded here because it is a decision, not a detail.
- **The phone cannot be the sync host.** Android suspends the WebView when the app is backgrounded, which tears down its sockets; holding a listener open needs a foreground service with a persistent notification and its own permission. So "the always-on device" means a machine, and a phone is not one.
- **All three transports are listed even though one is built.** Home server works; Syncthing and a hosted file say "not yet". The list is the decision, and an option that silently does nothing is worse than one that admits it is not there. The snapshot format is identical across all three, so switching is pointing at a different address.
- **A blocked permission is said once, not once per tap.** "Turn on notifications for Sorted in your phone settings" appeared every single time a reminder was switched on. The condition was already right — it only appears when the system itself reports `denied`, which is exactly "notifications are off for Sorted at the phone level", and it never appears when they are on. The fault was repetition: after the first time it is not information, it is an obstacle between someone and the switch they were trying to move. It is now remembered per permission state and cleared the moment notifications are allowed. Separately, once a check has come back `denied` the app stops calling `requestPermissions` — a refusal is an answer, and asking again does not change it — while still re-checking, so a user who has been and turned notifications on is picked up without being asked again.
- **A card's total belongs on its heading line.** The four breakdown cards on Reports each spent a whole line on a total row under the bars. On a phone that is about a fifth of the card, saying something the heading already implies: "Spending by Category … £123.00". The label went with it — "Total Spent" beneath a heading that says Spending said it twice.
- **A setting that names itself does not need a heading.** Currency, People, Reminders and About each gave a line to a title their own contents already made obvious — "Currency", "Add someone", "Bills due / Record spending / Savings goals". Removing the title is what `Appearance` and `Passcode` already did. Data Management and Danger zone keep theirs: they hold several controls that need naming, and a card that can delete everything should not be the one that lost its label.
- **The currency's own code sits beside its picker.** "Currency  GBP  [v]" — without the code the dropdown is the only thing saying which currency is in use, and it has to be opened to find out.
- **One definition per name, across all the scripts.** `toggleBillsReminders` and `changeNotifyTime` were each defined twice: once in notify.js, once in app.js. Plain `<script defer>` tags share one global scope and app.js loads last, so app.js silently won — including its copy of the Bills Due handler, which repainted *after* two bridge calls and so undid the fix recorded below. The flag cleared, the switch stayed on, and toggling a different row forced the repaint that finally showed the truth: exactly the "crossed wires" that were reported and not reproducible by reading the handler. There is now a test that fails if any name is declared in two of these files, because nothing else in the build notices.
- **A switch's repaint must never queue behind a bridge call.** (Restated because it was fixed once and then silently reverted by the duplicate above, which is the strongest argument for the test above.) Order is record the choice → repaint → *then* talk to the platform. The flag used to be written first with the repaint after `await requestPermissions()`, and on Android that request puts a system dialog on screen, so the switch did not move until you changed tabs.
- **A card's spacing comes from its container, not its own margin.** `.reports-grid` already had a 20px gap and `.report-card` also carried `margin-bottom: 14px`. Inside a grid those add rather than replace, so Reports and Settings ran at 34px between cards where the dashboard ran at 20. The margin is gone and the padding is now 20px to match `.stat-card` exactly.
- **Every item row is three lines, and the right column is the amount alone.** Bills rows carried a fourth line — the timing — under the amount, which made them 101px against Spend's 91px: ten pixels of difference on every row, so every tab change jumped. The left of a row is only about 164px once the amount and the tick have taken theirs, so the timing had nowhere to go but onto the date line. That forced the countdown to lose words — "Due today" said "due" twice with the date beside it, and "overdue" became "late" on a row that is already tinted red. A paid bill says "Paid 4 Oct", without the year, for the same reason: the line has no room for both. Savings income, accounts and goals were brought onto the same three-line shape, with their qualifier line (`item-timing`) carrying what used to sit under the amount.
- **A very long title still wraps, and that is accepted.** A title that needs two lines makes a taller row on both tabs equally. Truncating someone's own words to preserve a pixel grid would be the worse trade. What had to go was the *systematic* difference between tabs, not the content-dependent one.
- **`narrowSymbol` is the right `currencyDisplay`, and six currencies need a hand.** Intl in en-GB has no symbol data for many currencies and silently prints the ISO code instead: 32 of the 47 read "CHF 12.00". `currencyDisplay: 'narrowSymbol'` fixes 26 of them and drops the region prefixes ("US$" → "$"), leaving six that have symbols Intl doesn't carry — BGN, AED, SAR, KES, MAD, PEN — supplied in `CURRENCY_SYMBOLS`. The Swiss franc is deliberately absent from that table: it has no symbol, so "CHF" is the correct answer and inventing one would be worse. An older WebView whose Intl rejects the option falls back to `symbol` rather than losing the currency.
- **The one destructive control looks like it.** "Start Over" is now "Danger zone", last on Settings, with a red border and a red heading. Source order matters: `.report-card` sets its border with a *shorthand* and both selectors are a single class, so a `.report-card--danger` rule placed before it is simply overwritten — which is exactly what happened, leaving a card with a red heading and an ordinary border.
- **Spend is a one-off, so it does not ask how often.** The Repeats control is gone from the Spend form and stays on Bills. It was held back for four releases because Standing Charges was built entirely from recurring spend; that card is gone now, so nothing is fed by it. Existing repeating spend rows keep their stored frequency — the field is only written when the form actually offers the choice, so renaming one can't quietly un-repeat it.
- **An activity list has to add up to the balance above it.** The account Activity view lists what moved an account. It opens with the opening balance and any adjustment, undated and after the dated entries, because a list of movements that visibly fails to reconcile with the balance it sits under is worse than no list. There is a test that sums the entries and compares.
- **A switch must not move under the finger.** "The Bills Due toggle off does not work — you can make it toggle off by toggling off both the other toggles." The flag cleared correctly and the switch re-rendered off; what broke it was that a row was `[label][picker][switch]` while on and `[label][switch]` while off, so turning one off slid the switch out from under a finger still resting on it. Three rows whose controls all shift is a very convincing "crossed wires". The picker is now always rendered and only greyed out, so the control column never changes width. This also fixed the separate complaint that the row height changed and everything below jumped.
- **The side rail is hidden by CSS loaded before the first paint.** The `is-native` class was added by app.js, which runs after the stylesheet has painted, so the widest thing on screen appeared for a frame and vanished. Now set on `<html>` by an inline head script, same as the theme, with the `body` selector kept so the two can't disagree.
- **Nothing before your first entry is knowable, so nothing is drawn there.** Stepping the forecast back on a young database produced a smooth plausible curve that was entirely fiction: the walk-back adds back bills and income it can see and subtracts spend it cannot. The series now starts at the earliest recorded date. Measured: three months back on data three weeks old returned 18 days instead of 92.
- **A currency is a display choice, not a stored one.** Figures were always plain numbers, so changing the symbol never touches a row or needs a migration. Fifty-one currencies, formatted through `Intl`, with the old hand-rolled format kept as the fallback for an unknown code or a browser without it — an amount is the one thing on a row that must always appear.
- **An unrecorded week is not a zero-spend week.** Both insights average over the weeks that *have* entries. Averaging across the whole eight-week window regardless made "your usual week" read as £35 when four recorded weeks said £70 — so every real week looked like an overspend and the card was permanently alarmed. The divisor is `recordedWeeks`, and below three the card says it needs more data rather than claiming a pattern.
- **A partial week is compared like for like.** This week is measured against the same number of days into previous weeks, so Monday morning isn't reported as an 80% saving.
- **A page builds its HTML in one template, so one bad name blanks the whole page.** A helper deleted while its call site stayed behind threw inside `renderReports` and left Reports empty. There is now a test that visits all six destinations against a near-empty database and asserts each puts content on screen with nothing logged — the only question that catches this class.
- **Receipt accuracy is a measurement, and the measurement changed the plan.** `ocr-bench.js` draws four receipts with known answers at three tilts and runs them through the real pipeline. Baseline: **10/12 amounts, 12/12 titles, 9/12 dates**. Two faults behind it: the amount fell back to "the largest number on the page", so a £8.60 receipt with `CASH 10.00` on it read back as £10.00; and `SUBTOTAL` contains `total`, so a discount between the two made the subtotal win. Fixed by ranking total-words, excluding tender lines, and borrowing a figure from the line below a bare `TOTAL`. Dates: Tesseract reads "2 Oct 2026" as "20ct 2026" — letter O as digit zero — so months are matched tolerantly and the zero folded back to an `o` before lookup, because stripping digits first reduced `0ct` to `ct`.
- **Upscale, but do not binarise.** Grayscale plus an Otsu threshold looked like the obvious preprocessing win and measured as a loss: it fixed decimals and dates on the grocery receipts while chewing dense low-contrast lines elsewhere, turning a loyalty balance of `2840` into `B40` and costing the one date that was still being missed. Upscaling alone scored 12/12 on both; upscaling with binarisation scored 12/12 and 11/12. The threshold code was deleted rather than left behind a flag. This is the case for measuring before keeping complexity — the "obvious" half was the one that hurt.
- **Never await the platform before repainting.** This took four releases and three wrong diagnoses. The saved setting was always correct — the switch just never repainted, because `turnReminderOn` wrote the flag and then awaited `requestPermissions()` *before* `renderPage()`, and on Android that call puts a system dialog up. The whole handler was awaiting a dialog, so the view could not update; switching tabs ran a fresh render that picked the saved value back up, which made it look like a stale-render problem. The order is now fixed and is the part worth remembering: record, repaint, *then* talk to the platform. Settling the schedule lives in its own function so nothing it does — a hang, a slow bridge, a rejection — can reach back and stop the view having already shown what was asked for. The regression test hangs the plugin permanently, which is the honest limit of the failure mode.
- **A control must not vanish because a permission is off.** Settings had a "permission denied" early-return that replaced the whole Reminders card with a paragraph. Asking for permission comes back denied, so the three switches disappeared rather than flipping; leaving the tab and returning rebuilt them from localStorage, which is why the saved state had always been correct and only the view was lying. The reported symptom — "they only work once I switch tabs and come back" — was this, not a stale render. The same early return was in the state line underneath, so a blocked browser was told nothing at exactly the moment it needed saying.
- **Zero is a real answer and a confusing one to read bare.** Android accepting a schedule with nothing due printed "0 reminders scheduled", which reads like a failure. It now says nothing is due yet and that the schedule will be used when something is.
- **A settings switch records the choice first and warns afterwards.** It briefly didn't: the flag was only written once the platform confirmed permission, so on a phone that answered unexpectedly — or threw, or was asked before anyone had granted anything — the toggle silently refused to move. You can act on a warning; you can't act on nothing. The flag is now written unconditionally, the permission asked for afterwards, and the discrepancy reported.
- **A permission message that vanishes in 3.5 seconds is one you can't act on.** `showToast` takes a duration; the messages that name a fix stay up for 8s, and the Settings line keeps the state on screen afterwards.
- **The permission state doesn't say whether the schedule worked.** `checkPermissions` reporting `granted` and Android quietly refusing to queue the alarm look identical from inside the app. Settings now also asks Android what it actually has pending and shows the count.
- **A refusal and a failure are different answers.** `enableNotifications` wrapped one `requestPermissions()` in a `try/catch` and returned `'denied'` for anything that went wrong, then the toast said "Notifications are blocked for Sorted". A missing plugin, a rejected bridge call and a user genuinely refusing were indistinguishable, so the real cause could never be reported from the outside. `notificationPermission()` now returns the platform's own state and `'unavailable'` is separate; only a real refusal says blocked, and in a browser that is still the true wording.
- **On Android, "denied" usually means the app's notification switch is off.** Android 13+ has two separate things — the runtime permission, and the app's notification switch in system settings — and `LocalNotificationsPlugin` answers with `NotificationManagerCompat.areNotificationsEnabled()`, i.e. the switch, not the permission. "If app is unused" is a battery setting and does not affect it. Only Android Settings can change it, so that is what the message and the button say.
- **Check before asking.** `notificationPermission` calls `checkPermissions()` first and returns immediately if already granted, so a user who allowed notifications in system settings gets the toggle working instead of a second prompt that may never appear.
- **A reminder's switch sets only its own flag.** Both toggles went through one function that always set the bills flag, so switching on the spending nudge silently switched on bill reminders.
- **Reminders are scheduled, and the schedule is derived.** `@capacitor/local-notifications` schedules real alarms, so they arrive with the app closed. The pending set is rebuilt from the database on every relevant write — pay a bill, record a spend, top up a goal, delete anything, wipe everything — rather than tracked incrementally, so what arrives cannot drift out of step with the data.
- **No exact alarms.** `SCHEDULE_EXACT_ALARM` needs its own user grant on Android 12+ and Play restricts it to alarm-clock apps. "You haven't recorded today's spending" does not need to land on the minute, so the schedule is inexact and asks for one permission fewer.
- **A goal nobody has observed is not stale.** The savings nudge counts days since a top-up, but a goal stores only its current figure — there is no history of contributions. Treating "never seen" as stale would fire on every launch; treating it as fine would leave the nudge inert for exactly the people whose goals already exist. The first launch stamps every existing goal as observed, so the clock starts instead of never starting.
- **A rule's position in the stylesheet is load-bearing.** `.form-input--mini` set `width: auto` and lost to `.form-input { width: 100% }` further down the file — same specificity, later wins. Every reminder picker went full-width and pushed its switch off the edge of the card.
- **A savings goal is a number you keep yourself.** There is no monthly target, because the app has no business inventing one. It used to fall back to "what's left, over the twelve months to a fixed horizon" — a real division by a horizon nobody could see — and asked people to approve it with "leave blank to work it out", "worked out from what's left and the time remaining", on a form with no end date to have a time remaining to. The field is gone and the fallback with it: a goal contributes to the forecast only if a monthly was explicitly set, and goals that had one keep it. Revisit with a target date if it is ever worth doing properly.
- **A tab opens at its own top.** `navigate()` never touched scroll, so every tab inherited the offset you left the last one at — worst on Reports, which is the longest page, where you land on a chart with no heading above it.
- **Money in a jar is not money you have.** The forecast ran `running += income + savings - bills - spend`, on the reasoning that savings isn't spending. True of Total est costs, which is bills plus spend and never included savings. Not true of "what you'd have": a plan to save £200 a month is £200 a month you will not spend, and adding it back reported a balance the money can't reach. It leaves now. A goal with no account is also taken off the starting balance, which it never was — its `current` was in no account to begin with, so it counted as spendable from money sitting in the jar.
- **A row is a table, not two blocks.** Spend and Bills carry the same three things in two columns — title, date, category on the left; amount, timing, icons on the right. Both columns used to pin their whole block to the top, so the category line landed wherever the block ended: 11px above the icons, and 14px on a row with no lozenge because the badge made that line 22px instead of 15px. `.item-row--lines` pins each column's first line to the top and its last to the bottom.
- **A confirm's state cannot live on the DOM it is confirming.** The Income repeat toggle kept its "tapped once" flag on the button element, so any re-render — including its own 4-second `renderPage()` — threw the offer away with no feedback. It lives in a module variable now, and the timer touches that one button instead of the page.
- **A control whose label changes needs a reserved width.** "Repeat monthly" is 53px wider than "Monthly", so the Income toggle slid sideways under the thumb on every tap and back again four seconds later.
- **The bill's value says when.** "Scheduled" replaced a countdown that was useful at every distance, which meant a row reading "Due 12 Oct" and "Scheduled" told you nothing you couldn't already read off the date. It counts down at every distance and becomes "Paid on ..." once ticked.
- **Every amount in the app sits in the same place.** One `.value-cell` class, fixed minimum width, last element in the row, with ticks, dots and paperclips in a `.row-actions` cell in front of it. Continuity of position was the point: an inline `text-align: right` per row drifts the moment someone adds a row.
- **Spend is for the one-offs, Bills is for what repeats.** The Recurring filter came off Spend, and each page carries a small "i" saying so.
- **The forecast arrows were the wrong way round.** `stepForecastMonth(-1)` for "back" clamped itself to a no-op at the current month while "forward" walked *further* into the past. The test that let it through asserted the clamp worked, never the direction.
- **Paying a bill settles it where it stands.** Until 2.8.3 it wrote a *payment* into Spend, rolled the bill forward and deleted it if one-off. That put the same money in two categories at once: the payment counted in the spending average while the bill counted again as a bill in every month it projected into — so a £500 rent was forecast at £1,000 a month, forever. A paid bill is still a bill, and stays in Bills marked paid.
- A **recurring** bill must therefore leave a fresh payable row behind when paid. Leaving only a projection would make next month's occurrence inert, with nothing to tap.
- Rows written before 2.8.3 are still read correctly: their payments are recognised in Spend as bills, so existing balances and histories keep working. The spending average excludes them, so they are not learned from as if they were ordinary spending.
- A settled bill is not projected, not outstanding, not overdue and not reminded about. Leaving any of those in counted it twice — the settled row *and* its own next occurrence.
- The forecast is a **running balance by day**, not monthly totals. A household cash flow forecast answers "will I have enough on this specific date", and the failure mode it exists to catch is timing: a bill on the 1st against pay on the 15th. Monthly buckets cannot show that fortnight, which is why 2.7.x drew the wrong chart.
- Every plotted line is an *amount as at that day* — the balance, and running totals of income, bills, spend and savings — so they share one scale with no second axis.
- The headline is the **lowest projected balance and its date**, not a monthly average. Days before today are rebuilt from records; days after are projected, with a dashed marker at today.
- A goal's default monthly contribution is worked out against a **fixed 12-month horizon**, never the window on screen. Deriving it from the window made the same goal read as £600/month in the 3-month view and £150 in the 12-month one, and the chart contradicted itself.
- Income is projected only for dates that **have not happened yet**. A salary already recorded is already inside the account balance, so projecting it forward too counted it twice.
- The monthly spending average uses only **complete** months. An unfinished month does not vote: £10 logged two days into the month was being averaged as a full month against six real ones, pulling the average down 15%.
- An account's **"Balance now"** is what the account holds today, and the editor converts it to the stored opening balance on save. The label and the stored field disagreed, so typing your real balance left the row showing something else.
- **Bills, Spend and Total est costs are month to date and reset on the 1st.** A running total across the whole window climbs without limit, so by August the line read "you have spent £21,000" — a bigger number, not a comparison. What is worth reading is how the current month is going, so each month starts again at nothing. On the 1st they are £0, except for bills actually due that day.
- **Income and Savings are not drawn.** They were clutter: two of six lines, one of them green like Total money, and their only visible job was to explain a jump the balance line already showed. They still contribute to Total money — income lands on its date and savings accrues daily — they are simply not plotted or keyed.
- The forecast plots one month at a time. Rolling the monthlies up turned a repeating £98 bill into a line climbing to £1,176 by August — a stable cost drawn as a growing problem.
- Total est costs = Bills + Spend. Savings was in it until 2.7.2, which inflated the figure and counted savings twice: a goal not attached to an account never left the balances, so the balance card and the forecast disagreed about whether it was still yours. Savings is money in a jar, not money spent.
- Total money = current account balances + that month's income + that month's savings. It is *adjusted* per month, never accumulated — last month's balance is already inside `opening`.
- Forecast inputs that cannot honestly be derived are derived anyway and left editable: monthly spending defaults to the average of the last six months (a bad forecast, and labelled as one), and each goal defaults to its remaining amount spread from its month of creation to the horizon.
- Transfers are off the forecast. Money between your own accounts is not income; counting both sides made the chart claim you earn what you spend. They still move balances, where they are real.
- The three cost lines can be too compressed to read when the balance is large, so each carries its figure in the legend.
- Removing something means removing it. Replacing a removed line with a different one explaining the new arrangement is not a removal, and it left the settings page carrying copy nobody asked for.
- Recurring items carry a `frequency` ('monthly' or 'annually') alongside the old `recurring` boolean, which is still read and written so nothing already stored has to be rewritten; `recurring: true` with no frequency means monthly, which is how those rows behaved. A recurring item projects its own occurrences into the months on screen, up to twelve months out.
- A projection is a forecast, not a record: dashed, no buttons, no row to open, and kept out of every total. It has no id, so there is genuinely nothing behind it to act on. The one check that matters is that a projection never appears for a month the item is already *stored* in — paying a recurring bill rolls its date into exactly the month it would have projected, so without that check a bill shows twice.
- `billsForMonth()` returns stored rows and projections as separate lists, never mixed. A caller that sums what a month costs has to be able to tell a forecast from a bill, and returning them in one list is how a projected amount ended up inside Total Due.
- There is no sample data. It seeded a new device with a mortgage, a co-op energy bill and a holiday fund, so handing the APK to someone else gave them a stranger's household to delete. Removed in 2.12.0 along with the `sorted-seeded` flag and the once-per-install guard. A first launch and "delete all data" now both land on empty.
- People are attribution, not accounts. A person is a name and a colour, and "who's using the app" is a localStorage setting like the theme — anyone can switch it, so it is a label, not a login. It exists because a shared family device otherwise cannot say whose spending is whose, and because "who paid for it" cannot be answered from a bill's own record.
- "Who's using the app" stamps new entries and bill payments; the form's person field is pre-filled from it and still overridable, so the common case costs no taps and the odd case (adding a bill in someone else's name) costs one dropdown. Paying a bill records the *payer*, not the bill's owner, because that is the half the bill itself can't answer.
- The person filter sits on Spend and Bills, one shared selection across both, so switching person in one place doesn't leave the other quietly showing a different slice. The Spend totals follow it (it's a filter on the same data); the Bills *Total Due* card deliberately doesn't, because a card dropping to £0 because of a filter reads as "nothing owed". Dashboard and Reports stay household-wide for the same reason — the household view is what they're for.
- Rows are new rows get a `crypto.randomUUID()` id rather than the store's `autoIncrement` counter. Two devices counting from 1 would eventually hand out the same number, and sync is a stated goal — better to pay that cost now than re-key every row later. The stores keep the key generator they were created with, so this needs no schema change; `put`/`add` with an explicit key simply never invokes it.
- Legacy rows have *numeric* keys, and a data attribute always hands an id back as a string — `"3"` is not the key `3`. `normaliseId()` turns a numeric string back into a number on read and delete, without which every row in an existing install silently fails to open.
- "Who Spent What" gives one bar per person: the length is that person's share of the household total, so the bars compare against each other, and the split inside each bar is their own spend-to-bills ratio, which the length alone can't show. Unattributed money is kept as its own "Anyone" row rather than dropped — the card rolls up the same spend and bills as the two category cards above it, and quietly leaving it out would make the three disagree.
- No person dot on the Who Spent What rows. The name is the identity, the fixed 104px name column already truncated longer names once a dot was added, and a third colour sitting beside a two-colour bar invites reading it as a third bar colour. The dot stays on the Spend/Bills rows, where there is no bar to confuse it with.
- Tesseract (63KB) and pdf.js (320KB) load on demand via `loadScriptOnce()`, when a receipt is picked, not on every page load. `defer` on the script tags was tried first and did almost nothing (85 -> 86): deferred scripts still run in order, so app.js waited on the bundles regardless. Fetching them only when needed cut the first load from 577KB to 200KB, LCP from 4.1s to 2.0s, and performance 85 -> 99.
- A person's PIN is additive, not a replacement: the app passcode keeps working exactly as before, so nobody can be locked out by the feature existing. Entering a person's PIN unlocks *and* switches to them, which is the only thing in the app that ties attribution to an action rather than a free choice.
- What a PIN is, stated plainly because it is easy to over-read: it identifies, it does not authenticate. Anyone who reaches Settings can reset anyone's PIN without knowing the old one, and can switch the top-bar chip afterwards anyway. A four-digit family PIN is not a security boundary, and the README says so rather than leaving it implied.
- A PIN alone locks the app (`isLockEnabled()`), and the People card says so when the app passcode is off. The alternative — a PIN that does nothing until an app passcode exists — is a feature that silently fails, which is the worst failure mode for something whose entire job is to be noticed. "Lock after" and "Lock now" follow the app lock rather than the app passcode, so they stay reachable when only person PINs hold it shut.
- Every PIN and the app passcode share one length. The lock screen's keypad shows a fixed number of dots and submits on its own, so it has to know the length before anything is typed; a four-digit PIN could never be entered through a six-digit pad. Changing the app passcode to a different length while PINs exist is refused rather than allowed, because the alternative is silently stranding every PIN already set.
- Two people cannot share a PIN, and a PIN cannot be the app passcode. A shared PIN would make the unlock ambiguous and attribute one person's spending to another — the one outcome this feature must never produce.
- Person PINs live in localStorage, like the app passcode: a device setting, not finance data, and deliberately not in a backup. A person removed from the app has theirs dropped, or the app would sit locked against someone who can no longer be selected.
- People come first on import, in both modes, and are matched by name: ids are minted per device, so a name is the only identity that survives the trip. Every `personId` in the file is then translated to the local id of whoever it matched, and an unmatched reference becomes unattributed rather than a dangling id the UI would render as a blank. `getAllData()` is driven off `STORES` for the same reason — people missing from a backup would strip every entry's attribution on the next restore.

**7. Design System**
- Shared base stylesheet source: jaquesbody/know repo, static/css/main.css — canonical copy. New projects duplicate the token/reset/typography/utility sections into their own repo (self-contained, no cross-repo runtime dependency); project-specific sections (e.g. "Portfolio homepage," "Under construction") are excluded from the copy, not carried forward.
- Sorted accent: #3d8bfd (blue) — chosen distinct from Know's #ff5c00 and the portfolio identity green #0EDA29.

**8. Icon Convention (exception to non-goal 8)**
- Non-goal 8 rules out icons except standard buttons (save/upload/edit). Exception carved out: compact status indicators where text would be repetitive or cramped at scale (e.g. many items in a list) may use a single, intuitive icon instead of a text label, provided the icon isn't a clickable action.
- Confirmed: outlined tick-box, fills solid when confirmed. This is the confirm/sign-off action itself, already covered by the original non-goal exception, not a new one. Drawn as an inline SVG rather than a "✓" character — the glyph rendered thin and inconsistently placed, and inside a circle it read as a radio button rather than a confirmation.
- Recurring: grey circular-arrow icon, present only on items that are recurring (absence = one-off, so no risk of reading as an inert button). Tap/hover reveals "recurring spend."
- Receipt: paperclip on every spend/bill row. Dimmed with no image behind it, where it is the way in to attach one; full strength when there's a photo to open. Shown on all rows rather than only those with photos so the row doesn't change shape once one is added.
- Person: a coloured dot with the first letter, in the row's action column beside the paperclip. A full name would not fit at that width, and the letter is what identifies it. This is the one place a non-action, coloured mark sits in a list row, and it is deliberately not one of the app's semantic colours — a red dot beside a number reads as "overdue" — so `PERSON_COLOURS` in db.js is a separate identity palette. Letter colour is picked from the dot's own luminance rather than assumed, so every swatch stays legible.

**9. Layout Notes**
- Pages have no `<h1>`. The nav bar already says where you are, and on a phone the heading was the single biggest thing between the top bar and the content. Each page's one control — the month navigator, the report range chips, a lone action button — sits in a toolbar row instead.
- The month selector is one component on three pages at a fixed width (`--month-nav-width`), because the same control in two widths reads as two different controls. The label is a button: tapping it returns to the current month, which is otherwise a long walk back with ▶.
- Category bars are a grid with a fixed name column, so a long name like "Entertainment" can't squeeze the bar it sits next to; the name truncates and keeps the full text in a title attribute. Bars carry the colour of what they break down — spending blue, bills red, savings green — because "Bills by Category" in spending blue read as a spending chart.
- Bills Due is scoped to a month because a bill is only ever stored with the date it's currently due — without stepping forward there was no way to see what the following months hold.
- The trend chart's month in view is marked with a band behind its column. That band needed its own token: `--bg-surface` works in dark but is the same white as the card in light, so the highlight vanished in the light theme.
- "Who's using the app" is a chip in the chrome, not in a page: the top bar on a phone, the sidebar header on desktop (only one is ever visible). It belongs in the persistent furniture because an attribution you have to go looking for is an attribution you forget to set. The person filter is a second row of the existing filter bar rather than a control of its own, with a negative top margin so the two read as one control on two axes.
- On a phone the sidebar collapses to a 60px icon rail, where `.nav-item span` is `display: none` — which took the accessible name with it, leaving six nameless icon buttons. They carry `aria-label` for the rail; the bottom bar keeps its visible text.
